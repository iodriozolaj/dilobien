          How the A/B tests work

          Test 1 — this page's headline. Half of visitors see a pain-focused headline ("you're stuck on what to say"), half see a benefit-focused one ("skip the awkward drafting"). Each page load logs an impression; clicking the CTA logs a conversion for whichever variant that visitor was assigned.

          Test 2 — the homepage CTA copy. Half of homepage visitors see "Join the waitlist", half see "Get early access" on the hero and nav buttons. A conversion is logged only when the visitor actually submits the waitlist form — see the homepage for that test live.

          Implementation note

          What matched the wireframe: the hero A/B headline with its variant tag, the three-card live proof row, the tag-filterable content grid, and the explainer box all shipped exactly as sketched — same layout, same order, same live-data behavior.

          What changed after the wireframe: the original wireframe only covered the hero, proof row, content grid, and A/B explainer — it didn't yet include Persona, Brand system, Landing copy, the 10 social posts, the 3 video scripts, or the 14-day calendar, since those requirements weren't reflected in the first draft. Those sections were added directly in code, following the same visual language (cards, soft-background alternation, the existing color tokens) so they read as part of one page rather than a bolted-on addition. The Copy/Export/Save action row is a new UI pattern not in the original wireframe at all, introduced because those three buttons are themselves a required deliverable.

          Variant assignment, the persona, the brand system, the landing copy, all 10 social posts, all 3 video scripts, and the 14-day calendar are plain exported data/functions on window.MarketingEngine, so the logic and content the page renders is exactly what the software tests call.
